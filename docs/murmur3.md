# MurmurHash3 variant and portability contract

The `murmur3` feature implements the complete MurmurHash3_x86_32 byte algorithm,
not an FNV digest with a Murmur finalizer. It reuses
[Quickwit's MIT implementation at 23fff70d](https://github.com/quickwit-oss/murmurhash32/blob/23fff70ddd628a1f47db5616f01e3bb3a9e8b1e7/src/murmurhash3.rs),
with bounded streaming and const evaluation added for normalized ICC headers.
The full MIT notice remains in `src/murmur3.rs`.

The variant is fixed on every architecture. Four-byte words and remaining
bytes are little-endian, arithmetic wraps at 32 bits, and the total byte length
is folded modulo 2^32. Empty input is finalized with the supplied seed.
`digest` neither consumes nor modifies state; update boundaries, empty updates
and input alignment do not affect the result. There is no x86/x64 dispatch.
The fixed x64_128 implementation is described below; no algorithm is chosen
from the host ISA.

Checked against the [Wikipedia algorithm description](https://en.wikipedia.org/wiki/MurmurHash#Algorithm)
and [Appleby's public-domain reference at 07bb4de1](https://github.com/aappleby/smhasher/blob/07bb4de10a63e8cc2e1724865454eba635742383/src/MurmurHash3.cpp).
Wikipedia distinguishes the 32-bit and two incompatible 128-bit variants; it is
context, while the pinned primary implementations and independent goldens are
the numerical oracles.

`tests/reference/murmur3.txt` contains 316 C++-produced golden pairs for the
explicit byte pattern `input[i] = (37*i + 11) mod 256`: lengths 0 through 67,
255/256/257, 511/512/513, 1023/1024 and 4095/4096/4097; seeds 0, 42,
3_242_157_231 and u32::MAX. Tests also retain Quickwit's seven published ASCII
pairs. They check one-shot hashing, streaming split positions, byte-at-a-time
updates, empty updates, digest snapshots, const evaluation and unaligned input.
The fixed expected digests are not generated by the Rust implementation.

`just murmur3-check` regenerates the fixtures using the unmodified pinned
SMHasher C++ sources and compares them byte for byte. Run that producer on a
little-endian host: the original C++ body loads native words. Rust tests always
read the committed little-endian goldens, including on big-endian targets.

The same suite runs with `--all-features` on Linux/Windows x86-64 and ARM64,
macOS ARM64, cross i686, cross s390x big-endian, and WASI with and without SIMD.
The isolated `tools/stability` package also runs it with only `murmur3` enabled
and throughout its feature powerset. no_std checking includes the new feature.
These tests establish the listed byte inputs; they do not claim a cryptographic
property or exhaustive coverage of all possible inputs.

The default feature set and MSRV are unchanged. No streaming `Hasher`/I/O
adapter, random seeding or host-dependent algorithm selection is added.


## Canonical x64_128, portable even on x86

Appleby defines three distinct functions: x86_32, x86_128 and x64_128. These
names record the designs' original optimization targets, not a requirement to
run on that ISA. x64_128 and x86_128 generally produce different results **on
the same CPU**. Empty input with seed zero is an example where both happen to
return zero; the functions are not interchangeable.

`murmur3_x64_128` always runs the canonical x64_128 mixing/finalization, with
little-endian 16-byte blocks, a zero-extended u32 seed in both accumulators,
64-bit wrapping arithmetic and byte length modulo 2^64. The return value is
`(h2 << 64) | h1`; its little-endian bytes match the reference's first word h1
followed by h2. Numeric hexadecimal prints h2 first, which must not be confused
with the byte string's order. The C reference accepts an int-sized length;
streaming here explicitly extends length accounting modulo 2^64.

There is no runtime ISA selection or implicit x86_128 fallback. Both fixed
algorithms stay portable and outside `nonportable`. The separate x86_128
algorithm is not exposed; the C golden producer records its outputs as a
contrast, preventing an accidental switch on 32-bit hosts.

`tests/reference/murmur3-128.txt` supplies 316 independent C-generated x64_128
pairs and the corresponding x86_128 contrast values, using the same lengths,
patterns and four seeds as the 32-bit corpus. Tests exercise all 16 tail sizes,
unaligned offsets 1–15, stream splits, clones, empty updates, repeated snapshots,
const evaluation and canonical output-word order. They run through the same
native, i686, big-endian, WASI and isolated no_std configurations as x86_32.

The canonical SMHasher VerificationTest schedule is also reproduced, checking
Appleby's published verification codes: x86_32 `0xB0F57EE3`, x64_128
`0x6384BA69` ([main.cpp at the pinned source](https://github.com/aappleby/smhasher/blob/07bb4de10a63e8cc2e1724865454eba635742383/src/main.cpp)).
This is an algorithm identity check, not a claim to have run SMHasher's entire
statistical suite. The 128-bit source is ported from Appleby's public-domain
reference; the 32-bit Quickwit MIT notice remains intact.

Zenpixels' existing ICC table still uses its documented `(FNV-1a64, x86_32)`
pair. Adding this 128-bit API does not silently change retained fingerprints
or the separately selected XXH3 pixel-hashing backend.
